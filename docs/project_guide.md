## 一张图经过系统时发生什么

图像与框标签 → 统一图像尺寸和类别编号 → Backbone 提取不同尺度特征 → Neck 融合特征 → Head 输出框和类别 → 置信度筛选与 NMS → 对照标注计算 Precision、Recall、mAP。

输入一般是 `[B,3,H,W]`。如果 H=W=640，P3/P4/P5 的空间尺寸通常为 80/40/20；实际通道由 YAML 的宽度倍率和模块配置决定，不能只背一组通道。小目标的轮廓可能在连续下采样中消失，多尺度融合试图同时保留位置细节和高层语义。

## 源码阅读路线

1. `train.py`：整理后的显式训练/验证/预测入口，要求传入真实配置与模型路径。
2. `yolohg.yaml`：读 `from, repeats, module, args` 四个字段，画出 P3/P4/P5 的来源。
3. `ultralytics/nn/modules/block.py::HG.forward`：多个尺度输入经 `PyramidPoolAgg` 聚合，再经卷积、AIFI、C2f，按通道切分为两个输出，其中一路上采样。
4. `ultralytics/nn/tasks.py::parse_model`：模块如何注册、如何处理 HG 输出及通道列表。HG 返回列表，不能直接按普通单张量层理解。
5. `ultralytics/engine/validator.py` 与 `ultralytics/utils/metrics.py`：预测如何与标注匹配，怎样得到 AP。

当前代码的 `__version__` 为 8.2.14；报告还出现 8.2.18、YOLOv11 等描述，而 YAML 明确包含 YOLOv8 风格的 C2f 结构。投递统一使用“基于 Ultralytics 的改进 YOLO”，不在缺少最终环境与检查点时强行认定为 YOLOv11。

## 实验与证据边界

技术报告和旧简历记录五类异常的 mAP50 为 99.5%、mAP50–95 为 84.9%。报告正文有 AP/AP50 对调以及不合理百分比等问题，本轮没有找到相匹配的原始验证日志。主简历采用五类异常适配与实验描述；如需写数值，明确是项目报告记录，不能声称本轮已验证。COCO 性能、全系统时延和消融收益不归入已确认的个人成果。

若训练与验证来自同一段视频的邻近帧，即使图像没有重名，仍可能存在场景泄漏。更稳妥的后续协议是按视频、设备或采集批次划分；这是改进建议，不是已经做过的实验。

## 2 分钟介绍

车载屏幕故障需要从图像中识别黑屏、花屏以及几种异常颜色。我的前期工作是完成小目标检测综述，比较不同结构怎样缓解弱特征、下采样和背景干扰。应用项目中，我参与 YOLO 算法模块设计与实验跑通。代码以 Ultralytics 的模块化配置为基础，输入经主干提取多尺度特征，在颈部融合后交给检测头。HG 模块对多个尺度进行聚合并输出两路特征，因此要同时检查 YAML 索引、模块注册和通道维度。我能说明个人参与的模型适配与实验流程，但不把整个桌面系统归为个人开发。原报告有较高的检测指标，当前缺少对应原始日志，因此投递以可确认的贡献和流程为主。

## 静态发现的网络接线缺口

HG返回列表，而所给YAML后续Concat直接引用此输出；parse_model对HG仅pass，缺少完整的多输出通道/选支处理。当前可能是中间源码，本轮未验证网络可构建，不按猜测重写最终架构。
